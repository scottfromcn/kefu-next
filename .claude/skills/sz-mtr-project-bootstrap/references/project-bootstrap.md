# Project Bootstrap Reference

## Standard Command

```bash
python tools/project-scaffold/create_project.py \
  --target <target-project> \
  --app <app-slug> \
  --display-name <display-name> \
  --domain <app-domain> \
  --backend fastapi \
  --frontend vite-react \
  --database mysql \
  --backend-port 8000 \
  --enable-oidc true
```

## Full Bootstrap Input Env

For end-to-end initialization, first copy and fill the private env template:

```bash
cp skills/sz-mtr-project-bootstrap/config/init-project.env.example \
  ~/.config/sz-mtr-project-bootstrap/<app>.init.env
```

The filled env file is the input contract for the full flow:

```text
local scaffold
  -> local validation
  -> GitLab project init or binding
  -> push main
  -> GitLab CI test
  -> build and push image
  -> generate deploy artifact
  -> test runner deploy
  -> health check
  -> return test URL
```

The filled env file may contain tokens and deployment details. Never commit it.

## Release Flow

Generated projects include the standard GitLab release flow:

```text
push main
  -> GitLab CI test
  -> build Docker image
  -> push to GitLab co-located Docker Registry
  -> generate deploy package artifact
  -> test server Runner pulls image and deploy package
  -> auto deploy test

manual approval / tag
  -> production server Runner pulls the same image and deploy package
  -> deploy production
```

Use server-side GitLab Runners on test and production hosts. Deployment hosts should initiate outbound access to GitLab and Registry; GitLab should not need inbound access to deployment hosts.

## Validation

```bash
bash -n deploy/*.sh
docker compose -f deploy/docker-compose.yml config
test -f docs/active-skill-flow.md
test -f docs/release-and-cicd.md
git status --short
```

The generated project should not contain real secrets, runtime data, database data, backups, or frontend build artifacts.
