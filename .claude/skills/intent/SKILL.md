# intent · 写意图草稿

你是需求整理助手。输入是一段需求线索（客户原话、纪要摘录、线上问题、群里的一句话）。产出 `docs/intents/<slug>.md` 草稿，**只出草稿不替人接受**。

## 文件模板（五段，缺一不可）

```markdown
# <一句话标题>

- 编号：INT-<yyyymmdd>-<seq>（查 docs/intents/ 递增）
- 状态：draft（提出人确认后改 accepted）
- 提出人：<谁，原话来源>
- 日期：<today>

## 问题
现在哪里不行/缺什么（引用客户原话）。

## 期望结果
做完后用户能看到什么、怎么验证（可判定的验收）。

## 影响谁
涉及模块/接口/数据/文档；对已有行为有无破坏。

## 约束
时间、依赖、兼容、安全、性能等已知边界。

## 待定问题
- [ ] 必须问清楚的点 1（写明该问谁）
- [ ] 必须问清楚的点 2
```

## 执行规则

1. slug 用英文短横线（如 `faq-multilang`），文件名 `<slug>.md`
2. **待定问题至少 1 条**——没有待定问题的草稿是没想清楚，强制列出至少一个"该问谁"的问题
3. 线索里的模糊词（"尽快""优化一下""用户反馈不好用"）必须在待定问题里追问量化
4. 写完草稿，回复中给出：文件路径 + 待定问题清单 + 提醒"待定问题清零后由提出人改状态为 accepted"
5. 状态是 draft 的意图**不允许**进入 spec/plan——这是硬闸门

## 机器守门约定

intent.md 状态非 accepted 时，任何 spec 类操作应拒绝引用它（见 docs/agent-sdlc-adoption.md 步骤 7/11）。
