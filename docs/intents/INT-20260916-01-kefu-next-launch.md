# kefu-next：Goal 模式驱动的轻量地铁客服系统（v1）

- 编号：INT-20260916-01
- 状态：accepted（提出人确认，2026-09-16）
- 提出人：产品负责人（原话："重新做个客服系统，别搞那么重，先能用；流程也得是简单的"）
- 关联 goal：docs/goals/v1-launch.md（验收 8/8 全绿）

## 问题

1. 现有 v0 代客服系统（sz-mtr-service-agent）按组织模板完整流程构建：mysql + 双服务容器 + nginx 规划 + React 工程 + 七阶段规范文档，交付周期数小时、运维面大——对"演示/试点/小站点"场景过重
2. 团队需要一套与 40 步完整流程**对偶的轻流程示范**：验收前置（Goal 模式），证明"可量化验证验收作为第一目标"能在 30 分钟内交付第一版可用系统
3. 两套流程（完整版/Goal 版）都需要活样本仓库支撑团队推广，不能只有 PPT

## 期望结果

1. 一个单容器、可公开访问的地铁客服系统第一版：聊天 + FAQ 召回 + LLM 引用作答 + SQLite 落盘 + 历史查询（验收以 docs/goals/v1-launch.md A1-A8 为准，全部可执行判定）
2. **流程产出物完整**：正式 intent（本文件）→ goal 文件（验收+回执）→ 单 commit 交付，形成与 v0 代同构但更轻的 `intent → goal → delivery` 链路
3. 对外可访问的示范仓库（public），任何人 clone 即获得：完整交付记录 + 12 个组织 skill + 守门钩子
4. 与 v0 代形成明确的**场景分工**（见"影响谁"），不是替代关系

## 影响谁

| 干系方 | 影响 |
|---|---|
| 团队新成员 | 先学 kefu-next（Goal 模式）再看 v0 代（完整流程），学习曲线降低 |
| v0 代（sz-mtr-service-agent） | 并存不替代：v0 = 维护期/跨模块/生产发布场景；本系统 = 0→1 交付/原型/演示场景；升档条件触发时产出物并入 v0 式流程 |
| 运维（本机生产服务器） | 新增端口 8182 与容器 kefu-next；SQLite 数据卷 `data/`，无 mysql 依赖 |
| 组织规范 | 继承 .claude/skills 与 .githooks（cp -r 复用，已验证可移植）；本仓库 public，代表组织门面，提交仍须过守门 |

## 约束

- **技术边界**（本期硬约束，防蔓延）：FastAPI 单文件；SQLite 单库；内嵌单页 HTML（不引 React/构建链）；单容器单进程；LLM 用 glm-4-flash（bigmodel 免费层）；FAQ 12 条继承 v0 代
- **流程边界**：走 Goal 模式（.claude/skills/goal），不走 40 步完整流程；守门只保留 pre-commit + 提交信息规范
- **安全边界**：public 仓库零密钥（key 只进容器运行时 env）；无鉴权仅限本机/内网演示，对外开放前必须先做鉴权 goal
- **端口**：8182（8180/8181 已被占用）
- **升级路径**：升档条件（牵连第二人/验收连续两轮定不出/动生产配置）任一命中即停 Goal 转 40 步流程
